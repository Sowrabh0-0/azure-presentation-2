Starting Point

What I Was Planning For

Problem framing

Business need

  • Move Opslora to an Azure-native platform without losing the existing GitHub/GHCR workflow.
  • Support test first, production later, and DR when the platform is mature enough.
  • Keep room for on-prem Hermes AI connectivity from Trivandrum.

Engineering need

  • Clear blast-radius boundaries.
  • Private networking for secrets and data.
  • Terraform that can be reviewed without guessing the active environment.
  • Cost-aware SKUs and phased rollout.

Resource Group Decision

Why I Split Resource Groups By Ownership

Operational grouping

What I chose

Network, security, connectivity, DNS, management, monitoring, AKS, ingress, data, and Terraform state are separated into focused resource groups.

Why it helps

RBAC, cost review, locks, diagrams, and Terraform plans become easier to understand and safer to operate.

What I avoided

One giant resource group would be faster today but risky later. Too many resource groups would be noisy. I chose the middle path.

Actual Azure placement still follows Azure platform constraints5 / 15

Decision logic

  • Environment roots define blast radius.
  • Modules encode repeatable Azure patterns.
  • main.tf should wire modules, not hide all resource logic.
  • Files are split by concern: providers, variables, locals, outputs, backend.
Rejected: one giant Terraform file7 / 15
Workspace Decision

Why I Did Not Use Terraform Workspaces

State safety

Why not workspaces?

  • Hub, test, prod, and prod-dr do not have the same resource shape.
  • Workspace mistakes can plan/apply the wrong environment.
  • Condition-heavy code makes review harder.
  • Prod safety should not depend on remembering the active workspace.

Chosen state model

platform/terraform.tfstate
test/terraform.tfstate
prod/terraform.tfstate
prod-dr/terraform.tfstate

Workspaces can still be used later for temporary preview stacks with the same shape.

Separate roots plus separate backend keys are clearer for real environments8 / 15
Terraform Mechanics

Depends On, Taint, Lifecycle, And Provider Aliases

Guardrails

depends_on

Use sparingly for Azure ordering not visible through attributes, such as RBAC propagation or DNS link readiness.

taint

Emergency break/fix only. Not a rollout pattern for AKS, MySQL, Firewall, or Application Gateway.

lifecycle

Use prevent_destroy for critical state/data. Use ignore_changes only for controller-managed fields.

Aliases

Use provider aliases for cross-subscription peering, DNS links, and hub-to-spoke operations.

Terraform should make risk visible, not hide it9 / 15

Data And Secrets

Private MySQL And Key Vault Are Platform Defaults

Security posture

MySQL Flexible Server

  • Use Azure Database for MySQL Flexible Server.
  • Use Advanced Create or Terraform, not Quick Create.
  • Use private VNet integration.
  • Use a delegated snet-mysql-flexible subnet.

Azure Key Vault

  • Real secrets stay in Key Vault.
  • No DB passwords, JWT keys, SMTP passwords, or tokens in Git.
  • AKS reads through CSI and workload identity path.
  • Prod disables public access after rollout.
Secrets in tfvars were rejected because they leak into files, logs, and state13 / 15

Final Operating Model

The Rollout Path Is Deliberately Phased

Next execution

Phase now

  • Hub foundation and test spoke first.
  • AKS with Azure-native monitoring, Key Vault, GHCR, and AGIC.
  • Validate app workflows end-to-end on app-test.opslora.com.

Phase next

  • Promote same pattern to prod after test is stable.
  • Add VPN connection once on-prem public IP, CIDR, and shared key are final.
  • Keep prod-dr as documented reserve, then warm standby when cost and maturity justify it.
Decision principle: use Azure built-ins where they reduce operational surface15 / 15
